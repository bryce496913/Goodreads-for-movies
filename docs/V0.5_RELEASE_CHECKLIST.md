## Local build and regression run

Open `MovieTracker.xcodeproj`, select the shared **MovieTracker** scheme, install an iOS 17+ simulator, and run:

```sh
xcodebuild -version
xcrun simctl list devices available
scripts/validate-v05.sh <INSTALLED_SIMULATOR_UUID>
```

The script creates a unique `/tmp/MovieTracker-v05.*` directory with Xcode version, destinations, Debug/Release build logs and the full Debug test xcresult. It uses `set -euo pipefail`, so a failing build/test does not disappear behind `tee`. It does not upload, delete data or produce a signed archive. Use dedicated test simulators; test stores/Keychain entries are isolated, but ordinary app installation has its own real sandbox. Record pass/failure/skip totals from xcresult, not the source inventory. Test screenshots are attachments, not pre-existing evidence.

## Team and bundle configuration

`Config/Beta.xcconfig` is the shared project base configuration. Copy `Config/Local.xcconfig.example` to ignored `Config/Local.xcconfig`, then set your **APP_BUNDLE_IDENTIFIER** and **DEVELOPMENT_TEAM**. The test bundle IDs derive from the app ID. Inspect effective settings for all targets in Xcode; retain `TEST_HOST`/`BUNDLE_LOADER` for hosted unit tests.

The tracked default remains `com.example.MovieTracker` to avoid silently moving earlier installations to a different sandbox. **It is not an approved distribution ID.** Changing App ID creates a different app/container; it does not migrate earlier data. Match the ID of an installed build when testing in-place upgrades, or preserve a device/simulator backup and test a copy. Never uninstall/reset a user store as a migration workaround. Build 12 must be increased if that number has already been uploaded for 0.5.0.

Set provider credentials **on the test device** in Profile → Settings after confirming provider authorization/retention requirements. Saved tokens use non-synchronizing, when-unlocked, this-device-only Keychain storage; changing/removing a token does not change library data. Saving validates token syntax, not provider authorization; test an actual request separately. Debug private Run-scheme `TMDB_READ_ACCESS_TOKEN` takes precedence when present. Release ignores that development environment override and uses the device Keychain. Do not embed tokens in xcconfig, Info.plist, source or shared schemes. Existing open detail models use their original service; reopen them after changing configuration.

## Archive, validate, and install

After every gate above is satisfied:

1. Sign into the correct Apple Developer account in Xcode, select the proper team and owned App ID, and confirm automatic signing/provisioning for the app and test targets. Confirm a paid program/App Store Connect access for TestFlight.
2. Set a unique build number. Recheck app display name, approved icon, supported iPhone/iOS target, Release settings, privacy manifest/report and export compliance. Do not use UI-test launch arguments or package developer credentials.
3. Select a registered physical iPhone for direct local Run, or **Any iOS Device (arm64)** / the current generic iOS destination for archiving.
4. Choose **Product → Archive** using the shared scheme (Archive action is Release). Alternatively, with your local signing configuration, use `xcodebuild archive -project MovieTracker.xcodeproj -scheme MovieTracker -configuration Release -destination 'generic/platform=iOS' -archivePath /tmp/MovieTracker-0.5.0.xcarchive`. Do not pass `CODE_SIGNING_ALLOWED=NO` for an uploadable archive.
5. In Organizer inspect the actual archive’s version/ID/signing, icon, privacy report and contents. Confirm no test fixture services/data or token values were included. Use **Validate App** and record the validation outcome. A successful simulator Release build is not an archive validation.
6. **Only with explicit upload authorization**, choose Distribute App → App Store Connect → Upload. Resolve validation/export-compliance errors; retain sanitized evidence. No archive or upload was produced in this task.
7. In App Store Connect create/select the matching app record, complete required beta/privacy/compliance fields, wait for processing, then select the build in an **internal testing group** and add authorized internal testers with appropriate roles. Do not publish externally or submit to App Review as part of this pass.
8. On a physical iPhone install TestFlight, accept the internal invitation, install the correct version/build, configure an authorized device token and run the complete journey/offline/relaunch checklist. Preserve data when updating builds; do not uninstall to simulate an upgrade.
